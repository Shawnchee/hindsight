# M0 hand review

You review the 40 sampled incidents in `m0/catalog/m0_sample.csv`. The CLI times each review and saves the labels. The summary turns those reviews into the numbers M0 exists to measure:

- **minutes per review**, which sets the M1 dataset size
- **Slither coverage**, meaning how often a Slither finding explains the exploit. This sets the ceiling for pure triage.

## Files

- `reviews.jsonl` holds one JSON record per review, appended. The latest record per incident wins. These are our own labels, so commit this file.
- `summary.md` is generated by `summarize.py`.
- `proposals.jsonl` holds the LLM-proposed labels, merged from `proposals.part*.jsonl`. Pressing Enter accepts a proposed value. The summary reports how often you overrode each field.

## Run

From the repo root (`/Users/shawnchee/Desktop/projects/hindsight`):

```sh
# 1. Once: fetch victim candidates, their Sourcify source, compile, and run Slither for every sampled incident.
#    The output goes to m0/data/review/ (gitignored).
VIRTUAL_ENV=$PWD/.venv .venv/bin/python -I m0/scripts/review/prepare.py \
    m0/catalog/m0_sample.csv m0/data/funnel/dhl m0/data/review

# 1b. Merge and validate the LLM label proposals (already done for this sample).
#     The CLI shows them as defaults. proposals.jsonl records the model that wrote each one.
python3 -I m0/scripts/review/merge_proposals.py m0/review/proposals.part*.jsonl

# 2. Review. Resumable: rerun it to continue. q = quit, s = skip.
python3 -I m0/scripts/review/review.py
python3 -I m0/scripts/review/review.py --list          # progress
python3 -I m0/scripts/review/review.py --redo <id>     # redo one incident

# 3. Summarize.
python3 -I m0/scripts/review/summarize.py --hours-per-week 3
```

## Per incident

1. Press Enter to start the timer. Then open the PoC (the path is printed) and read the write-up.
2. Pick the victim contract from the candidates.
   - Use `m` to type in an address that isn't listed.
   - Use `-` if none of the candidates is the victim.
   - Sourcify finds many victims; the rest need Etherscan. If the victim has no source, Slither can't run on it. That's still a valid review.
3. Say whether it's a code-level bug. Key compromises, rugs and frontend attacks are out of scope.
4. Set the root cause, mechanism and impact. They're separate fields: a flash loan is a mechanism, not a root cause.
5. Enter the causal locations, for example `Vault.sol:withdraw`, each with a role (defect, entry point or affected).
6. Adjudicate the Slither findings:
   - which findings **explain** the exploit
   - which are other **confirmed valid** issues
   - which are **confirmed invalid**

   Anything you leave unmarked counts as `unresolved` and is excluded from precision.
7. Enter the minutes you were interrupted. They're subtracted from the time.

The DHL label and PoC header are **label evidence**. Use them freely here, but they never go into eval inputs (PRD ENR-6).
